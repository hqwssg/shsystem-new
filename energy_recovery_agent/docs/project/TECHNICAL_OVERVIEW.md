# Shuohuang Railway Regenerative Energy Dispatch Technical Overview

## 1. Project Background

> Current implementation note (2026-08-25): the unified entry point is `python run_project.py` and the default runtime dataset is `data/real_shuohuang/`. This document retains the earlier technical background and model evolution; the current status, input/output contract, and validity boundary are maintained in [`docs/current_project_status_and_io.md`](../current_project_status_and_io.md) and [`docs/current_algorithm_validity_boundary.md`](../current_algorithm_validity_boundary.md). Older `data/real_partial`, 594 km, and long-downhill examples are historical/virtual examples and must not override current runtime metadata.

This project studies a train dispatch algorithm for regenerative braking energy recovery on the Shuohuang Railway heavy-haul corridor.

The target operating pattern is:

- Loaded heavy trains run downhill and generate regenerative braking energy.
- Empty trains run in the opposite direction and consume traction energy while climbing.
- A flexible traction power supply system enables energy transfer within specific power supply sections.
- Battery storage can absorb unused regenerated energy, but storage has capacity, efficiency loss, and depreciation cost.

The dispatch objective is to improve energy utilization while maintaining train operation performance and safety.

The project started as a virtual-data prototype. It also retains `data/real_partial`, a historical Shuohuang-only mixed dataset extracted from `列车运行图及技术资料.pdf`. The unified entry point now defaults to the rebuilt `data/real_shuohuang`; `real_partial` is kept for compatibility and traceability, not as the current result basis. Both datasets use explicit placeholders, heuristic parameters, or planning assumptions for unsupported fields. Current results are suitable for workflow and constraint-integration verification, but not yet for engineering-grade dispatch conclusions.

## 3. Train Simulation Model

The simulator is implemented in `train_simulator.py`.

The project initially used a point-mass train model. This has been upgraded to a length-aware multi-segment equivalent model.

For each train:

- The train head position is tracked over time.
- The full 2.7 km train length is divided into multiple sampling points.
- Each sampling point independently reads:
  - route gradient
  - curve radius
  - flexible power supply section occupancy
  - long downhill section occupancy
- Total gradient resistance and curve resistance are summed across all train segments.

This solves the issue where the train head may already be on a downhill section while the tail is still on flat or uphill track.

Direction handling (the 594 km endpoint below is historical virtual baseline; runtime uses the selected data directory's route endpoint):

- Heavy trains run forward from 0 km to 594 km.
- Empty trains run reverse from 594 km to 0 km.
- For reverse-running trains, route gradient sign is reversed from the train's operating perspective.

This allows the same physical route section to represent downhill regenerative braking for loaded trains and uphill traction demand for empty trains.

## 4. Energy Settlement Model

Energy settlement is implemented in `energy_settlement.py`.

The model separates train power into:

- regenerative braking power
- traction consumption power
- direct energy use within flexible power supply sections
- battery charging
- battery discharging
- wasted regenerative energy
- grid purchase energy

Important principles:

- The entire railway is not treated as one global regenerative energy zone.
- Only the configured flexible traction power supply sections allow direct energy transfer and storage participation.
- If a train is only partially inside a flexible power section, only that proportion of train power can participate in coordinated energy use.
- Regenerated power outside the flexible power sections is counted as wasted energy.
- Traction demand outside the flexible power sections is counted as grid purchase.

Battery parameters include:

- capacity
- maximum charge power
- maximum discharge power
- round-trip efficiency
- depreciation cost per kWh
- grid purchase price

The settlement engine supports configurable time buckets through `settlement_time_step_s`.

- `1s` gives the most detailed result.
- `10s` or `30s` can be used for rolling optimization speed.
- Final candidate schedules can be re-evaluated with `1s` precision.

## 5. Safety and Signaling Constraints

Safety constraints are implemented in `scheduler_nsga2.py`.

The project no longer relies only on a simple departure headway constraint. It now supports a configurable signaling system:

- fixed block
- moving block
- hybrid fixed plus moving block

Current default:

```json
{
  "mode": "hybrid",
  "fixed_block_length_km": 2.0,
  "fixed_block_protection_blocks": 2,
  "moving_block_base_buffer_m": 500.0,
  "moving_block_reaction_time_s": 30.0,
  "moving_block_follower_service_decel_mps2": 0.28,
  "moving_block_lead_emergency_decel_mps2": 0.5,
  "check_step_s": 5
}
```

Fixed-block protection:

- Maps train head and tail positions to block indices.
- Requires a configured number of protection blocks behind the lead train.
- Supports both forward and reverse train directions.

Moving-block protection:

- Computes distance from lead train tail to following train head.
- Compares it with a dynamic braking safety distance.
- The safety distance includes:
  - base buffer
  - reaction time distance
  - braking-distance difference between follower and lead train

This signaling model is still based on virtual capacity assumptions. Real engineering deployment should replace it with actual block boundaries, station interlocking, throat constraints, turnouts, and route locking data.

### 5.1 Station and Section Resource Constraints

The prototype now includes a virtual station/section resource layer in `resource_constraints.py`.
It derives resource occupation from train trajectories and station chainage.

Covered resources:

- interstation section occupation by direction
- optional single-line/shared section occupation
- station arrival/departure track capacity
- station throat/route locking capacity
- same-direction section capacity conflicts
- opposing-direction section conflicts
- station track capacity conflicts
- throat route conflicts
- same-direction overtaking/order-reversal checks

Each conflict explanation includes:

- conflict type
- resource id/name
- train ids/types
- overlap start/end/duration
- mileage/location
- human-readable message
- suggested dispatch adjustment

`rolling_optimizer.evaluate_schedule` and `RollingOptimizer` can now accept an optional `ResourceModel`.
When provided, resource conflicts make a candidate schedule infeasible.
`tests/legacy/verify_resource_constraints.py` writes verification outputs to `outputs/resource_constraints`.

## 6. Optimization Framework

The current project includes two layers of optimization.

### 6.1 Original NSGA-II Module

The original NSGA-II implementation is in `scheduler_nsga2.py`.

It can still optimize a small fixed number of train departure times. However, directly optimizing hundreds of train departure variables is not suitable for realistic Shuohuang Railway operations because of dimensional explosion.

Therefore, the project now uses a reduced-dimensional dispatch strategy layer.

### 6.2 Low-Dimensional NSGA-II Strategy Optimization

The main rolling dispatch framework is implemented in `rolling_optimizer.py`.

Instead of optimizing every train departure time directly, it optimizes a compact dispatch template:

- heavy train headway
- empty train headway
- heavy-empty phase offset
- flexible-zone hold time
- number of heavy trains in the rolling window
- number of empty trains in the rolling window

These parameters generate a full departure plan inside the optimization window.

The low-dimensional optimizer uses a lightweight NSGA-II implementation:

- non-dominated sorting
- crowding distance
- tournament selection
- crossover
- mutation
- Pareto candidate extraction

Optimization objectives:

- average operating cost
- headway deviation
- worst-case scenario cost

This reduces the search space from hundreds of train-specific variables to a small set of interpretable dispatch strategy variables.

## 7. Robust Scenario Evaluation

The dispatch plan is evaluated under multiple disturbance scenarios.

Current default scenarios:

- normal operation
- heavy train departure delay
- empty train departure delay

The framework can be extended with:

- temporary speed restriction
- low adhesion due to rain or snow
- reduced traction or braking capability
- storage device state-of-charge abnormality
- blocked station or section

The optimizer uses average cost and worst-case cost so that selected schedules are not only energy-efficient under the nominal scenario but also more robust under disruptions.

## 8. MPC Rolling Optimization

The project supports Model Predictive Control style rolling optimization in `rolling_optimizer.py`.

Workflow:

1. Read current time, locked departures, train delays, and system state.
2. Optimize a future horizon, for example 2 hours.
3. Execute only the near-term window, for example the next 10 minutes.
4. Lock executed or committed departures.
5. Move the time window forward.
6. Re-optimize using updated train positions and delay information.

This is more realistic than computing a full-day static timetable once.

The rolling framework is suitable for:

- real-time delay recovery
- short-term energy matching
- dynamic empty-train departure adjustment
- storage-aware dispatch
- future integration with dispatch command systems

## 9. Performance Optimization

The project includes two performance improvements:

1. Time-bucket energy settlement
   - The settlement engine can aggregate energy by 10s or 30s buckets.
   - This reduces candidate evaluation time during rolling optimization.

2. Cached downsampled power series
   - Train simulation is run once per train type.
   - Power and trajectory series are cached.
   - Downsampled base series are cached by time step.
   - Candidate schedules only shift cached series by departure time.
   - The process-wide memo is a thread-safe bounded LRU (64 trajectories by default), with eviction counters, so long-running multi-scenario processes cannot retain every full trajectory indefinitely.

In current tests, 10s settlement reduced one rolling NSGA-II evaluation from about 14.24s to about 5.45s with the same demo result.

## 9.1 Engineering Solver Enhancements

The optimizer now includes several engineering-oriented controls beyond the original virtual NSGA-II/MPC prototype.

Energy settlement enhancements:

- initial battery SOC
- target final SOC
- final SOC tolerance
- final SOC deviation penalty
- wasted-energy penalty

These terms allow MPC to avoid strategies that appear cheap only because they end with an empty battery or discard regenerated energy. With default parameters disabled, the model remains backward compatible with earlier experiments.

Search and evaluation enhancements:

- `TemplateSearchConfig.parallel_workers` controls optional batch candidate evaluation.
- `batch_evaluate_templates` evaluates candidate templates in deterministic order and checks that parallel evaluation preserves objective values.
- `run_engineering_solver_experiments.py` runs SOC/waste-penalty optimization, a larger MPC window, and a batch-evaluation benchmark.

Current engineering experiment outputs are written to `outputs/engineering_solver`:

## 10.1 Operating Condition Physical Constraints

The prototype now includes physical operating constraints for low adhesion, weather, and temporary speed restrictions.

Implemented capabilities:

- `operating_conditions.py` defines weather rules, explicit low-adhesion zones, and temporary speed restriction rules by mileage and time window.
- `train_simulator.py` applies these rules during every simulation step.
- Weather can reduce the adhesion coefficient and increase rolling/aerodynamic resistance.
- Temporary speed restrictions replace the global line speed with the most restrictive active speed limit over the sampled train length.
- Adhesion limits cap both available traction force and available braking force.
- The simulator uses a look-ahead speed target so trains brake before entering a lower-speed temporary restriction.
- `scheduler_nsga2.py` uses adhesion-limited braking deceleration in moving-block safety distance calculations.
- Time-dependent operating conditions are evaluated by actual departure time, so a train departing later can meet different weather or speed-restriction windows.
- `tests/legacy/verify_operating_constraints.py` compares dry baseline and adverse-weather scenarios and writes verification data to `outputs/operating_constraints`.

The current adverse virtual scenario includes rain over the mountain section, a wet low-adhesion flexible power zone, and an 80 km/h temporary speed restriction. In the latest verification run, the heavy train's moving-block minimum gap increased from 3 minutes to 4 minutes under the adverse scenario, showing that low adhesion now affects safety separation rather than only adding a cost multiplier.

## 11. Known Limitations

The current model has partial PDF real-data integration, but it remains a mixed-data prototype.

Missing real data:

- official line gradient and curve data
- complete section chainage, turnout chainage, and station speed-limit mapping
- real block boundaries
- station throat and turnout constraints
- official train operation diagram
- actual daily train counts and train pairing logic
- real traction and braking curves
- actual flexible power supply equipment parameters
- actual or approved planned storage capacity, power limit, and control strategy
- disturbance statistics

Current simplifications:

- The train model is a multi-segment equivalent model, not a full longitudinal dynamics model.
- Coupler forces and in-train longitudinal impacts are not simulated.
- Station/section resource conflicts are modeled with a virtual capacity layer, but real interlocking, route locking, turnout topology, and yard data still need official data.
- Flexible power transfer is represented by section occupancy ratio.
- Battery model includes maximum charge/discharge power, but the values in the historical `data/real_partial` bundle (and corresponding defaults in `data/real_shuohuang`) are planning/sensitivity assumptions and need confirmation before engineering use.
- The signaling and resource models are simplified capacity models and should be replaced by actual block, interlocking, route-locking, and station topology data when available.
- Empty-train mass is scenario-dependent and should be analyzed through empty/light/mixed return scenarios rather than treated as one fixed true value.

### 12.1 Real-Data Input Interface

The project now includes a real-data ingestion layer in `data_ingestion.py`.
It accepts a directory of CSV/JSON files and converts them into the existing runtime objects used by the simulator and optimizer.

Input files:

- `route_metadata.json`: total route length, max speed, long downhill range, and signaling defaults
- `stations.csv`: station names and chainage
- `segments.csv`: line geometry by mileage, including gradient, curve radius, terrain, and optional static speed limits
- `energy_transfer_zones.csv`: flexible traction power / regenerative transfer sections
- `signaling_blocks.csv`: actual or virtual block boundaries, direction, block type, and single-line flags
- `station_resources.csv`: station track capacity and throat capacity
- `trains.csv`: heavy and empty train parameters
- `battery.json`: storage capacity, power limits, efficiency, depreciation cost, and grid price
- `operating_conditions.json`: weather, low-adhesion zones, and temporary speed restrictions
- `resource_config.json`: default station/section resource parameters

`train_simulator.load_config()` can now read either the original `sandbox_config.json` file or a real-data input directory.
`load_real_data_bundle()` additionally returns a `ResourceModel`, so station/section capacity data can be passed directly into the rolling optimizer.

The generated virtual template is located at `data_templates/shuohuang_virtual`.
It preserves the current virtual assumptions but uses the same file format expected from future official data.

### 12.3 One-Command Dispatch Case Pipeline

`run_dispatch_case.py` provides an end-to-end dispatch evaluation pipeline.
It can use either `sandbox_config.json` or a real-data input directory.

Pipeline stages:

1. Load and validate input data.
2. Build heavy and empty train power caches.
3. Generate a conservative baseline schedule.
4. Run rolling NSGA-II template optimization.
5. Evaluate baseline and optimized schedules with signaling, resource, and energy constraints.
6. Write comparison tables, time-series data, charts, and a Chinese Markdown report.

Default output directory:

```bash
python run_dispatch_case.py --input sandbox_config.json --output-dir outputs\dispatch_case
```

Main outputs:

- `optimized_schedule.csv`

## 13. Current Conclusion

The current project is a relatively complete algorithm prototype with partial Shuohuang PDF real-data integration.

It can support:

- technical route demonstration
- algorithm feasibility explanation
- virtual and partial-real mixed scenario experiments
- Pareto strategy comparison
- rolling dispatch workflow demonstration
- later replacement with fuller real engineering data

It should not yet be treated as an engineering-grade dispatch system. The current PDF data covers station topology at a line-list level, terminal boundary, selected speed/headway constraints, representative heavy-train mass, and technical-operation candidates. Official route geometry, train dynamics, signaling/block, station-route, power-supply, storage, and timetable/task data are still needed for calibration and engineering verification.

# 生产运行保障手册

## 1. 适用范围

本手册覆盖算法数据库任务服务的部署前检查、启动、日常运行、停止、升级、回滚和证据归档。当前可以完成本地工具验证和预案固化；目标服务器、正式账号、TLS、监控平台、正式备份介质和业务联调仍需甲方环境。

任何本地报告只能使用`local_ready=true`或`PENDING_EXTERNAL`表述，不得写成“已上线”“生产验收通过”或“满足生产SLA”。

## 2. 角色与职责

| 角色 | 主要职责 | 当前责任边界 |
| --- | --- | --- |
| 数据库管理员 | 建库、迁移账号、备份恢复、容量和慢查询 | 目标环境待甲方指定 |
| 平台管理员 | 平台账号、任务接口、界面状态和工件下载 | 待平台联调 |
| 算法运维 | worker进程、版本、资源档位、日志和任务恢复 | 本项目已提供工具与预案 |
| 调度业务负责人 | 不可行方案处置、人工接管和结果批准 | 待甲方指定 |
| 安全负责人 | TLS、密钥、审计和账号周期 | 待甲方指定 |

生产账号必须分离为迁移、平台、worker和只读查询四类。算法worker不得持有建表、建角色或平台任务创建权限。

## 3. 上线前顺序

1. 核验完整算法包、SHA-256和接口冻结版本。
2. 由密钥系统注入连接串，禁止写入配置文件和命令历史。
3. 部署数据库迁移和最小权限角色；生产连接必须启用TLS。
4. 运行`database_healthcheck.py`和四账号权限探针。
5. 发布不可变数据版本，正式数据未通过门禁时只能标记`planning_placeholder`。
6. 运行五类任务分角色验收、目标测试库压力与故障演练。
7. 完成备份恢复实操并记录恢复时间、备份哈希和恢复点。
8. 启动受进程管理器托管的worker，接入日志和告警。
9. 平台验证状态、结果、不可行扣留和下载审计。
10. 责任方完成`production_assurance_acceptance_checklist.md`并签字后才允许切换生产流量。

统一本地预检：

```powershell
python tools/production_assurance_preflight.py `
  --output-dir outputs/production_assurance_preflight
```

未提供数据库时，工具只验证本地可准备项，并固定输出`production_accepted=false`。

## 4. 启动与停止

启动前确认：数据库健康检查通过、迁移版本为`001-007`、worker ID全局唯一、心跳60秒小于租约300秒、磁盘未达到Critical、没有处于维护窗口的数据库操作。

常驻入口：

```powershell
python tools/run_database_worker_loop.py
```

生产环境必须使用Windows服务、systemd、容器编排或甲方进程管理器托管，配置异常自动重启、标准输出采集和优雅停止。停止时先暂停平台新建任务，再等待当前任务完成或由平台显式取消，最后向worker发送`SIGTERM`/服务停止信号。禁止直接删除`running`任务或清空结果表。

## 5. 日常检查

建议每分钟采集一次运行快照：

```powershell
python tools/production_operations_snapshot.py `
  --database-url $env:SIMULATION_READONLY_DATABASE_URL `
  --output-dir outputs/production_operations_snapshot
```

每班至少复核：pending数量和最老等待时间、活动任务心跳、过期租约、24小时失败率、数据库与工件容量、主机磁盘、worker实例数和版本。监控平台应读取JSON并按`severity`路由告警，不要从Markdown抓取数值。

## 6. 任务恢复与人工接管

- 租约过期：先确认旧worker已停止，再执行`python -m database.cli recover-expired --max-attempts 3`。
- 任务取消：使用`cancel-run`并填写原因；迟到worker结果会被租约令牌拒绝。
- 连续失败：达到3次后保持`failed`，不得无限重试。
- 滚动任务`withheld_infeasible`：平台不得下发新计划；根据`safety_state`等待新观测或升级人工处置。
- 相同业务请求重试：必须复用原`idempotency_key`和完全相同内容。

## 7. 升级

1. 宣布维护窗口并暂停新任务。
2. 等待活动任务归零，保存运行快照和发布包哈希。
3. 备份数据库并验证备份目录可读。
4. 在隔离恢复库执行恢复演练。
5. 部署新代码包，先运行源码/包校验和接口冻结检查。
6. 使用迁移账号执行仅向前迁移，再运行健康检查。
7. 执行五类验收，确认结果合同和状态机未变化。
8. 灰度启动一个worker，观察至少一个完整最长任务周期。
9. 无Critical告警后逐步恢复worker和平台流量。

## 8. 回滚

代码回滚只允许回到与当前数据库schema兼容的已校验包。数据库迁移没有破坏性down migration；若迁移后无法继续，立即停止平台写入和worker，保存错误证据，按已验证备份恢复数据库，再部署与恢复点匹配的软件包。不得手工删除迁移记录、业务表或列。

## 9. 证据归档

每次上线或演练至少保留：软件包和SHA-256、策略版本、数据库迁移清单、健康检查、账号权限报告、运行快照、五类任务报告、压力/故障报告、备份SHA-256、恢复演练结果、开始结束时间、操作者和批准人。连接串、密码和私钥不得进入归档。

# 扰动后的局部恢复性修复

更新时间：2026-09-07

## 1. 功能定位

本模块完成扰动恢复的第二阶段。第一阶段先提取核心场景冲突链、锁定列车和冲突相关未来列车；第二阶段只把后者作为调整变量，在生成后的合并运行图上按 `H001...`、`E001...` 的列车编号直接修改发车时刻。

实现入口为 `recovery_repair.repair_recovery_schedule()`。它不修改已经发车或显式锁定的列车，也不调整与当前冲突无关的未来列车。

## 2. 求解目标与边界

局部搜索按以下词典序评价：

1. 不产生涉及范围外列车的新冲突；
2. 清除涉及允许调整列车的资源冲突和车流连续性问题；
3. 清除同方向最小追踪间隔违反；
4. 减少剩余可调冲突重叠时长；
5. 在达到相同恢复效果时，最小化最大单车调整量；
6. 再最小化全部列车的总绝对调整量。

默认以30秒为调整步长，单车最大调整范围为正负600秒，并采用有界波束搜索。调整后必须保持同方向列车顺序，发车时刻不能早于当前滚动时刻。正式平台接入后，这两个调整参数应作为版本化运行规则配置，不能被解释为现场已确认值。

## 3. 结果状态

| 状态 | 含义 | 是否可宣称自动恢复可行 |
| --- | --- | --- |
| `not_required` | 当前允许范围内没有需要调整的冲突 | 是，但仍以完整稳健评价为准 |
| `fully_repaired` | 所有核心场景中的可调冲突均清除，且没有锁定残余 | 是 |
| `partially_repaired_locked_residual` | 可调冲突已清除，只剩双方均锁定的历史冲突 | 否，需要运营干预 |
| `partially_improved_unresolved` | 约束负担已下降，但仍有未解除冲突 | 否，需要扩大恢复范围或运营干预 |
| `repair_failed` | 允许范围内没有找到更好的局部调整 | 否 |

主优化器只在常规核心稳健搜索没有可行候选时触发该修复器。修复结果还会经过完整的能量、电气、信号、资源和SOC稳健评价；只有它优于原稳健回退结果时才会采用。部分改善可以作为较低违反度的回退方案，但不会被标记为可行。

## 4. E15 四轮验证结果

| 轮次 | 修复状态 | 采用 | 调整 | 修复后结论 |
| ---: | --- | --- | --- | --- |
| 1 | `not_applicable` | 否 | 无 | 常规搜索已稳健可行 |
| 2 | `fully_repaired` | 是 | `H002 +90s`、`E002 +120s` | 3个可调冲突清零，整轮恢复稳健可行 |
| 3 | `not_applicable` | 否 | 无 | 常规搜索已稳健可行 |
| 4 | `not_applicable` | 否 | 无 | 常规搜索已稳健可行 |

第2轮名义修复时刻叠加本轮已观测重车晚点后，实际提交的 `H002` 为3570秒。第四阶段修正计划/实际状态提交口径后，四轮均通过核心稳健门禁、锁定历史不变、SOC连续、执行窗口推进和结果结构核验。该结果不证明当前占位参数下所有扰动都能自动恢复。

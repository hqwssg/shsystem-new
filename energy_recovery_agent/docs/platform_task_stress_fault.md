# 平台任务压力与故障测试

更新时间：2026-09-09

## 1. 目的与范围

本测试验证平台通过PostgreSQL创建、领取和管理算法任务时，在并发请求和工作进程故障下是否保持任务唯一、状态可追溯、租约隔离和结果事务完整。测试直接使用真实PostgreSQL多连接和数据库事务，但不执行耗时算法本体，因此测得的是平台任务队列能力，不是算法计算吞吐量。

测试工具强制数据库名称以`_test`结尾，拒绝连接业务库。数据库连接串仅从`SIMULATION_TEST_DATABASE_URL`环境变量读取，统一命令和报告不会保存连接串。

## 2. 运行方式

```powershell
$env:SIMULATION_TEST_DATABASE_URL='<专用测试库连接串>'
python run_project.py test-platform-tasks
```

调整负载：

```powershell
python run_project.py test-platform-tasks `
  --task-count 500 `
  --worker-count 24 `
  --idempotency-burst 64 `
  --output-dir outputs/platform_task_stress_fault_500
```

默认门禁为所有创建、领取、心跳和取消操作P95不超过2000毫秒，领取吞吐不低于10项/秒。阈值用于发现明显故障，不是目标平台SLA；部署环境应根据实际并发量重新设定。

## 3. 压力矩阵

| 项目 | 默认规模 | 验证内容 |
| --- | ---: | --- |
| 并发创建 | 120任务、12连接 | 唯一任务全部创建，无错误和丢失 |
| 同键幂等突发 | 32次 | 相同请求只形成一个`run_id` |
| 同键异内容冲突 | 12次 | 全部返回状态冲突，不覆盖原请求 |
| 并发领取 | 12个worker | `FOR UPDATE SKIP LOCKED`下每项只领取一次，不领取外部任务 |
| 并发心跳 | 全部已领取任务 | 当前令牌全部续租成功 |
| 并发取消 | 全部已领取任务 | 全部进入`cancelled`且活动租约清零 |
| 生命周期审计 | 全部压力任务 | 状态版本按0、1、2连续，无重复或缺口 |

逐次操作记录中位数、P95、P99、最大时延、worker和错误信息，可用于后续比较不同数据库配置。

## 4. 故障矩阵

| 编号 | 故障注入 | 必须满足的结果 |
| --- | --- | --- |
| `PF-F01` | 工作进程崩溃并强制租约过期 | 任务重新排队，由新令牌领取且尝试次数增加 |
| `PF-F02` | 旧进程迟到执行心跳、冻结快照、写失败、写结果 | 四类操作全部被拒绝 |
| `PF-F03` | 活跃任务被平台取消 | 租约立即失效，迟到结果不能覆盖`cancelled` |
| `PF-F04` | 同一任务连续三次崩溃 | 前两次重排，第三次达到上限转`failed` |
| `PF-F05` | 结果投影写入部分表后由数据库触发器抛错 | 全部结果表回滚，任务仍为`running`且无结果哈希 |
| `PF-F06` | 复合故障完成后审计状态事件 | 状态版本连续，终态与故障路径一致 |

## 5. 当前发现与修复

压力测试首次运行发现：相同幂等键并发创建时，确定性`run_id`可能先触发主键冲突，而原SQL只处理`(project_id, idempotency_key)`唯一约束，导致部分平台重试抛出`UniqueViolation`。现已将插入改为处理任一唯一冲突，再锁定读取既有任务并核对`request_sha256`；相同请求复用，异内容请求仍拒绝。

2026-09-09在本地PostgreSQL 16专用测试库完成三档实测：

| 任务数 | 并发worker | 同键突发 | 创建吞吐/项每秒 | 领取吞吐/项每秒 | 创建P95/ms | 领取P95/ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 120 | 12 | 32 | 937.633 | 732.541 | 14.861 | 12.026 |
| 500 | 24 | 64 | 1656.062 | 1418.456 | 16.172 | 17.389 |
| 1000 | 32 | 96 | 1923.173 | 1635.591 | 17.993 | 21.925 |

三档均为全部任务唯一领取、全部心跳成功、全部取消成功、无活动租约残留、状态事件连续、六项故障通过和测试项目清理成功。容量汇总见`outputs/platform_task_stress_fault_scale_matrix/PLATFORM_TASK_STRESS_SCALE_REPORT.md`。这些数值仅作为当前测试机基线。

## 6. 输出

| 文件 | 用途 |
| --- | --- |
| `PLATFORM_TASK_STRESS_FAULT_REPORT.md` | 压力指标、时延和故障矩阵结论 |
| `platform_task_stress_fault_summary.json` | 全部配置、门禁、时延、状态和限制 |
| `platform_task_operation_samples.csv` | 每次创建、领取、心跳、取消和幂等请求的时延 |
| `platform_task_fault_cases.csv` | 六项故障注入及结构化证据 |
| `platform_task_stress_fault_failures.json` | 压力错误和失败案例 |
| `platform_task_stress_fault_scale_matrix/` | 多档结果合同核验和容量对照 |

每轮创建独立测试项目和数据版本，结束后删除数据库中的测试项目、任务和结果；报告保留在文件系统中。

## 7. 仍需目标平台验证

本地测试不能替代目标环境的TLS连接、网络断开、数据库重启/主备切换、连接池上限、磁盘满、WAL压力、备份恢复和真实算法进程并发。目标平台部署后应使用相同工具重跑任务队列压力，并另行执行基础设施级故障演练。

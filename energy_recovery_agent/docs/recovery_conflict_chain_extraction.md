# 扰动恢复冲突链与可调整列车提取

更新时间：2026-09-07

## 1. 阶段目标

本模块完成扰动后恢复性修复的第一阶段，只负责回答“哪里发生冲突、哪些冲突彼此关联、哪些列车还能调整”。它不在本阶段修改运行图，也不声称已经消除冲突。

实现入口为 `recovery_conflict_analysis.extract_recovery_conflict_analysis()`。输入包括当前候选运行图、核心扰动场景、资源模型、重空车轨迹缓存、当前时刻和已锁定发车集合。

## 2. 决策边界

列车按资源检查器相同的顺序编号为 `H001...` 和 `E001...`：

- 发车时刻早于当前时刻，或发车时刻存在于显式锁定集合中的列车，标记为 `locked=true`；
- 当前时刻及之后且未显式锁定的列车，标记为 `adjustable=true`；
- 已锁定列车只能作为冲突原因和边界条件，不能进入后续发车调整变量；
- 不参与当前冲突的未来列车仍保留在 `all_adjustable_train_ids`，但不会进入冲突修复优先集合。

## 3. 冲突链定义

每个资源冲突形成一条连接两列车的边；同一列车参与的冲突通过图连通关系合并为一条冲突链。跨核心场景出现的同一组列车仍属于同一条链，但各场景冲突实例保留，不进行静默去重。

每个冲突实例按轮次稳定编号为 `CF001...`，每条链编号为 `RC001...`；冲突实例直接记录所属 `chain_id`，冲突链同时记录包含的 `conflict_ids`。每条链还输出涉及列车、锁定列车、可调整列车、场景、资源、冲突类型、累计重叠时长和首末冲突时刻，并采用三级判定：`repairable_by_future_departure_adjustment` 表示链内每个冲突都有可调端；`partially_blocked_by_locked_history` 表示只能修复其中一部分；`blocked_by_locked_history` 表示整条链均无法靠未来发车调整消除。

纯锁定冲突不会被错误放入可调整集合，而是标记为需要行车组织、线路资源或人工处置。

## 4. 可调整列车优先级

`adjustment_candidates` 只包含与冲突链相关的未提交列车，排序规则依次为：

1. 与锁定列车发生冲突的次数降序；
2. 参与冲突的累计重叠时长降序；
3. 最早冲突时刻升序；
4. 原发车时刻和列车ID升序。

每个候选同时携带 `priority_rank`、`chain_ids`、冲突次数、锁定对端冲突次数和累计重叠时长。第二阶段局部修复器可直接按此顺序构造调整变量。

## 6. 输出

结果位于 `paper/experiments/E15_synthetic_rolling_rescheduling/`：

| 文件 | 用途 |
| --- | --- |
| `recovery_conflicts.csv` | 逐场景、逐冲突实例审计 |
| `recovery_conflict_chains.csv` | 冲突图连通链摘要 |
| `recovery_adjustable_trains.csv` | 全体列车的锁定和可调整分类 |
| `recovery_adjustment_candidates.csv` | 第二阶段可直接使用的有序候选 |
| `recovery_conflict_analysis.json` | 完整结构化接口 |

正式系统接入后，列车ID应替换为平台稳定业务ID；当前 `H/E+序号` 只在同一张滚动运行图内稳定。

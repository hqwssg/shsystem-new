# 运行准备度与上线前质量检查

**版本：** v1.0  
**更新时间：** 2026-09-09  
**对应工具：** `tools/operational_readiness_checks.py`  
**性质：** 离线契约和质量门禁，不连接现场系统，不改变默认算法逻辑

## 1. 目的与边界

本检查用于正式数据到位之前，验证算法外围的“可运行性”和“可审计性”：实时状态输入是否符合约定、正式数据缺失时是否明确阻断、能量结果是否能追溯到来源、运行清单 schema 是否被错误版本污染，以及轻量结算是否出现明显性能回退。

它不能替代正式数据验收、车辆参数标定、供电臂实测、储能设备联调或现场实时性认证。检查通过的含义是工具链和内部账本满足当前契约，不代表已经获得现场节能结论。

## 2. 运行方式

```powershell
python tools/operational_readiness_checks.py --output-dir outputs/operational_readiness_checks
python tests/smoke/verify_operational_readiness_checks.py
```

工具返回码为 0 才算通过，并生成：

- `operational_readiness_summary.json`：机器可读的逐项结果、错误明细和性能数值；
- `OPERATIONAL_READINESS_CHECKS.md`：人读摘要。

## 3. 检查项

### 3.1 实时状态输入契约

`validate_realtime_snapshot` 检查单条状态，`validate_realtime_batch` 追加跨记录规则。每条记录至少包含：

| 字段 | 约束 | 目的 |
|---|---|---|
| `timestamp_s` | 非负整数秒 | 保证时间轴可排序，拒绝 NaN/无穷和小数时间戳 |
| `train_id` | 非空字符串 | 关联同一列车的历史状态 |
| `direction` | `forward` 或 `reverse` | 明确里程单调方向 |
| `position_km` | 非负有限数 | 统一线路里程坐标 |
| `speed_mps` | 非负有限数 | 防止负速度进入功率模型 |
| `power_kW` | 有限数，可正可负 | 正值表示牵引，负值表示再生/制动 |
| `soc_kwh` | 可选；非负且不超过容量 | 接入储能状态时防止越界 |

同一列车的时间戳必须严格递增；正向里程不得倒退，反向里程不得前进。单条记录或跨记录规则校验失败时都不会更新该列车的历史游标，避免坏数据污染后续判断。批量结果中的 `error_count` 与 `errors[index]` 可直接定位原始记录。需要新鲜度、断流和恢复语义时使用 `realtime_state_guard.py` 的 `RealtimeStateGuard`。

### 3.2 异常与降级策略

检查在空临时目录中调用 `validate_all(..., require_official_data=True)`，确认缺少正式数据时返回无效并包含错误，而不是悄悄用默认/虚拟文件补齐。当前策略是“严格模式阻断发布，开发模式可显式运行合成数据”；降级必须由调用方明确选择并在输出中标记数据状态，不能由界面或脚本隐式切换。

### 3.3 结果解释与能量来源追踪

检查构造一个关闭直供的储能场景，验证每个能源汇总行同时具有 `source`、`metric`、`value` 和 `reason`。并验证当前 `storage_no_direct` 口径下的两个守恒关系：

```text
total_gen_kwh == battery_charge_kwh + wasted_kwh
total_con_kwh == battery_discharge_kwh + grid_kwh
```

正式结果应沿用同样的来源分类（再生、储能、电网、损耗），并在报告中说明限制原因（容量、功率、供电臂、SOC 或时空不匹配）。该检查只验证账本可解释和可对账，不证明参数来自现场。

### 3.4 运行清单/schema 兼容性

当前门禁接受 schema `1.1` 且 `status` 为 `success/failed`、`return_code` 为整数的清单；未来主版本（如 `2.0`）或格式损坏的清单会被拒绝，防止旧解析器把新字段误读为旧口径。真正升级 schema 时，应同步更新解析器、样例、迁移说明和回归夹具，不应直接放宽检查。

### 3.5 性能门禁

使用 300 个时间序列重复结算 5 次，以中位耗时作为稳定指标，当前阈值为 `< 0.2 s`。该阈值用于发现意外回退，不是生产 SLA；不同硬件、Python 版本和正式规模必须另做容量分析。性能改动只有在该门禁和算法回归指纹同时通过时才可合入。

## 5. 接入实时系统前仍需完成

1. 与现场接口方确认时间戳精度、时区、列车 ID 生命周期和方向编码；
2. 消息乱序、重复、断流、恢复和时钟漂移的离线40项矩阵已经完成；目标消息中间件和现场时钟环境仍需按相同语义联调；
3. 将容量、供电臂和储能设备 ID 从正式配置注入，而不是由校验调用方手工传参；
4. 定义实时计算超时、重试、熔断和人工接管策略；
5. 正式数据验收通过后，在隔离目录执行仿真、结果审计和至少三次可复现运行；
6. 通过现场联调和安全审批后，才能讨论控制指令下发。

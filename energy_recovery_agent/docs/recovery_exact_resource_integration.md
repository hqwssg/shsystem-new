# 扰动恢复精确资源求解接入

更新时间：2026-09-07

## 1. 第三阶段目标

扰动恢复第三阶段把现有 MILP 精确资源可行性求解器接入滚动恢复流程。它解决第二阶段局部波束搜索仍未找到资源可行解时的结论缺口：区分“局部搜索遗漏可行解”“显式求解域内模型无解”“锁定历史已经使自动恢复不可能”和“求解时限内未知”。

实现入口为 `recovery_repair.solve_exact_recovery_schedule()`，生产调用位于 `RollingOptimizer.optimize_once()` 的局部恢复之后。

## 2. 合并运行图与锁定边界

滚动运行图同时包含已提交历史列车和当前窗口新列车，而原精确求解入口接收完整 `ScheduleTemplate`。第三阶段新增无损适配：

1. 把重车、空车完整绝对发车序列编码为全列车模板；
2. 生成后逐项校验，确保模板能够原样重建合并运行图；
3. 当前时刻之前及显式锁定的发车上下界固定为同一个值；
4. 其余未来列车才进入精确调整域，并保持同方向顺序和最小追踪间隔；
5. 求解结果回映为稳定的 `H001...`、`E001...` 逐车调整记录。

因此，精确层不再因滚动窗口带有历史列车而跳过，也不会把只有当前窗口列车的模板误当成完整运行图。

## 3. 触发和采用规则

执行顺序固定为：常规稳健搜索、第二阶段局部恢复、第三阶段精确恢复。

- 局部恢复已经实现核心稳健资源可行时，不再调用 MILP；
- 若第一阶段已经发现双方均锁定的冲突，返回 `blocked_by_locked_history`，不运行无意义的精确搜索；
- 其他局部恢复未完成情形调用 `solve_quality_optimized_resource_feasibility()`；
- 精确层覆盖容量为1及多容量资源，按最小最大单车偏移、再最小总绝对偏移求解；
- 精确候选先由权威资源检查器复核，再执行完整能量、电气、信号、服务数量和SOC稳健评价；
- 只有完整稳健评分优于当前回退结果时才采用；求解异常或超时只写诊断，不中断滚动流程。

`model_infeasible` 只证明输出中明确记录的时域、扰动集、锁定条件和当前输入下无解。`solver_limit_no_solution` 仍表示未知，不能解释为无解。

## 4. 验证结果

专项回归 `tests/smoke/verify_exact_recovery.py` 覆盖：

- 合并运行图无损编码和重建；
- 锁定列车固定、未来列车精确调整及逐车回映；
- 双方锁定冲突在求解前升级为运营干预；
- 求解器异常安全降级；
- `RollingOptimizer.optimize_once()` 在常规搜索和局部修复失败后调用并采用精确候选；
- 使用当前朔黄线路资源、车辆轨迹缓存、核心扰动集和 HiGHS 后端的真实求解，结果为 `feasible_verified`，已锁定重车发车保持不变。

E15 四轮测试中，第2轮由局部恢复完全解决；第四阶段修正实际执行状态提交后，第3轮强扰动和第4轮恢复状态均由常规搜索保持核心稳健可行。因此四轮均不需要实际调用精确MILP。专项回归继续独立验证带锁定历史的真实HiGHS求解和主优化器采用路径，避免把“本组场景未触发”误解为精确层不可用。

## 5. 输出

E15结果目录新增：

| 文件 | 说明 |
| --- | --- |
| `exact_recovery_results.json` | 每轮精确状态、证明、作用域、锁定边界、完整评价与采用状态 |
| `exact_recovery_decisions.csv` | 精确候选实际产生的逐车发车调整；无候选时只有空表头/空文件 |

当前列车编号仍是单张滚动运行图内的顺序编号。正式平台接入后必须改用稳定业务列车ID，并由正式规则确定精确求解时限、最大调整范围和允许提前发车边界。
